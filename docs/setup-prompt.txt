## Phase 4 — Configure `.env`

Work in the project root. Compose reads `.env` from there automatically.

- If `.env` exists, keep every line in it. Only add what is missing below.
- Port: if 8090 is taken (and not by Calivi itself), add `CALIVI_PORT=<a free port>`.
- CALIVI_SECRET_KEY signs sessions AND encrypts the secrets stored in the database. It lives in one of two places: in `.env`, or — when `.env` does not set it — in a file the backend generated at `/data/secret_key` inside the `calivi-data` volume. An existing install always has a key; an empty variable does not mean it runs without one. Decide by these cases, and never replace a key that exists:
    * `.env` sets it → leave it alone.
    * No `calivi-data` volume exists yet (fresh install) → generate one with `openssl rand -hex 32` and write it straight into `.env` without echoing it (e.g. `printf 'CALIVI_SECRET_KEY=%s\n' "$(openssl rand -hex 32)" >> .env`), then `chmod 600 .env`.
    * A `calivi-data` volume exists and `.env` does not set it (also when there is no `.env` at all) → do NOT add a key. The key is in the volume; once the backend runs, confirm with `docker exec calivi-backend test -f /data/secret_key && echo present`. A new key would make every stored credential unreadable, so do not suggest generating one either: moving the key out of the volume is done with the README section "Set CALIVI_SECRET_KEY if you back up the data volume", which carries the old key over.
- COOKIE_SECURE stays at its default (`false`): this setup serves plain HTTP, and `true` over HTTP makes login fail silently. If I told you Calivi will sit behind an HTTPS reverse proxy, set `COOKIE_SECURE=true` instead.
- Leave the optional stdio MCP bridge off. It is opt-in and runs third-party code.
